# Contributor Workflow

## Purpose

This file defines my standard workflow when using Claude Code to implement an assigned GitHub issue in an open-source repository.

Follow this workflow together with all repository-local instructions.

Repository-local instructions always apply. If repository policy conflicts with this workflow, follow the repository's explicit contribution requirements and report the conflict when relevant.

---

## 1. Issue Scope

I will provide a GitHub issue that I have been assigned to implement.

Treat the GitHub issue as the source of truth for the requested change.

Before modifying code:

1. Read the issue completely.
2. Read relevant issue comments and acceptance criteria when accessible.
3. Read the repository's applicable instructions.
4. Inspect the relevant implementation and tests.
5. Understand the existing architecture before making changes.

Implement **only what is required to resolve the assigned issue**.

Do not:

- fix unrelated bugs;
- perform unrelated refactors;
- upgrade dependencies without a requirement;
- reformat unrelated files;
- modify unrelated CI/CD configuration;
- change unrelated APIs;
- add speculative features;
- change project architecture unnecessarily.

If an unrelated problem blocks the implementation, do not silently expand the scope. Report the problem and ask for permission before making unrelated changes.

---

## 2. Repository and Git Safety

Before making changes, inspect the current repository state.

Verify:

- current repository;
- current branch;
- working-tree status;
- configured remotes;
- `origin`;
- `upstream`, when available;
- relevant default/base branch.

When contributing through a fork, use this convention:

- `upstream` = original repository;
- `origin` = my fork.

The implementation branch should normally be based on the upstream repository's default branch.

Never push implementation work directly to the upstream repository unless I explicitly have permission and the contribution workflow requires it.

---

## 3. Branch Naming

Use a normal human contributor branch name.

Preferred format:

```text
fix/<issue-number>-<short-description>
```

or, when appropriate:

```text
feat/<issue-number>-<short-description>
docs/<issue-number>-<short-description>
test/<issue-number>-<short-description>
chore/<issue-number>-<short-description>
```

Do not use AI, assistant, vendor, or tool identifiers in branch names.

Examples of prohibited identifiers include:

```text
claude/
anthropic/
copilot/
ai/
openai/
cursor/
gemini/
```

Do not add such identifiers to an otherwise normal branch name.

If I explicitly provide a branch name, use that exact name unless it violates repository policy.

---

## 4. No AI / Tool Attribution

Do **not add AI, assistant, vendor, or tool attribution to the contribution** unless the repository explicitly requires such disclosure.

Do not add AI/tool/vendor identifiers to:

- branch names;
- commit messages;
- PR titles;
- PR descriptions;
- source-code comments;
- documentation;
- generated files;
- changelogs;
- repository metadata;
- contributor metadata;
- filenames;
- release notes.

Do not add phrases such as:

```text
Generated by Claude
Created with Claude
Co-authored-by: Claude
Co-authored-by: Anthropic
AI-generated
Generated by AI
Claude Code
Anthropic
OpenAI
Copilot
Cursor
Gemini
```

unless the repository's contribution policy explicitly requires the information.

Do not modify Git identity or contributor identity to create or remove attribution.

Do not falsely claim authorship, credentials, testing, or review that did not occur.

If the repository explicitly requires AI disclosure, follow that repository requirement rather than this section.

---

## 5. Implementation

Implement the smallest correct solution that satisfies the issue.

Prefer:

- existing project patterns;
- existing abstractions;
- minimal changes;
- readable code;
- maintainable code;
- backwards-compatible behavior where appropriate;
- tests that verify the issue's behavior.

Do not introduce new dependencies unless they are necessary and justified by the issue.

Do not rewrite working code merely for stylistic preference.

---

## 6. Tests and Validation

Before implementation, establish a useful baseline when practical.

After implementation, run the repository's relevant validation.

Use the repository's own documented commands first.

Depending on the project, this may include:

- unit tests;
- integration tests;
- end-to-end tests;
- type checking;
- linting;
- formatting checks;
- compilation/build;
- static analysis;
- security checks.

Only report a check as passing if it was actually run and passed.

Clearly distinguish:

- PASS;
- FAIL;
- WARNING;
- NOT RUN;
- PRE-EXISTING FAILURE.

Do not claim that tests, coverage, builds, or static analysis passed when they were not actually executed.

Do not fix unrelated pre-existing failures unless required to complete the assigned issue.

---

## 7. Diff Review

Before committing:

1. Inspect the complete Git diff.
2. Confirm that changes are relevant to the issue.
3. Remove accidental changes.
4. Check for debug code.
5. Check for secrets or credentials.
6. Check for unnecessary dependency changes.
7. Check formatting and project conventions.
8. Confirm the issue's acceptance criteria are addressed.

The final diff should be focused and explainable entirely in terms of the assigned issue.

---

## 8. Commit

Create a concise, conventional commit message appropriate for the change.

Examples:

```text
fix: prevent duplicate CSRF refresh requests
fix: validate wallet public keys with StrKey
feat: add recurring donation date handling
test: cover proposal execution authorization
docs: clarify contributor setup
```

Do not include AI/tool/vendor identifiers in commit messages unless explicitly required by repository policy.

Do not create misleading authorship or co-authorship metadata.

---

## 9. Push

When working through my fork:

```text
upstream → original repository
origin   → my fork
```

Push the implementation branch to `origin`.

Do not push the implementation directly to `upstream` unless explicitly authorized and required by the repository workflow.

Before pushing, verify the destination.

---

## 10. Pull Request Handoff

The final PR remains under human control.

Claude Code must **not**:

- merge the PR;
- approve the PR;
- self-review/approve the PR;
- close the issue;
- force-push unless explicitly requested;
- make unrelated changes after the implementation is complete.

After successfully pushing the branch, provide:

- branch name;
- commit hash;
- files changed;
- tests/checks run;
- important validation results;
- upstream repository;
- base branch;
- fork repository;
- head branch;
- GitHub compare/PR URL.

Prefer providing a GitHub compare URL that allows me to review the changes and create the PR myself.

I will review the diff and create the PR.

---

## 11. Stop Conditions

Stop and ask me before continuing when:

- the requested behavior is ambiguous and cannot reasonably be determined from the issue/repository;
- the issue appears to require unrelated changes;
- the repository or issue cannot be verified;
- the correct base branch is unclear;
- the working repository is not the expected repository;
- pushing would target the wrong repository;
- repository instructions conflict materially;
- a required change would introduce significant architectural scope not described by the issue;
- credentials, secrets, or permissions are required unexpectedly.

Do not guess when a consequential decision is unclear.

---

## 12. Completion Report

When implementation is complete, provide a concise report containing:

### Implementation

- Issue addressed
- Summary of the solution
- Files changed

### Validation

- Tests run
- Lint/type-check/build/static-analysis results
- Any pre-existing failures

### Git

- Branch
- Commit
- Push destination

### PR Handoff

- Upstream repository
- Base branch
- Fork repository
- Head branch
- GitHub compare/PR URL

Do not claim completion until the implementation has actually been validated and pushed successfully.

---

## 13. Priority Order

When deciding what to do, use this priority order:

1. Repository contribution/security instructions
2. Explicit issue requirements and acceptance criteria
3. Existing repository architecture and conventions
4. This contributor workflow
5. General coding preferences

When instructions conflict, follow the higher-priority requirement and explain the conflict when necessary.

---

## Core Principle

**Implement the assigned issue, keep the diff focused, validate the work, push only to the correct destination, and hand the PR back to me for human review and creation.**
